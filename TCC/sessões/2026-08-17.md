# Sessão 2026-08-17 — Verificação da API do PNCP

## Resumo

A única incógnita capaz de derrubar metade do projeto foi resolvida antes de
qualquer linha de código: a API pública do PNCP **entrega preço unitário por
item**, sem credencial. Mas não pela interface que a documentação de consulta
anuncia, e com três armadilhas que produzem resultado incompleto sem sinalizar
erro. A verificação também produziu o argumento que sustenta o recorte
acadêmico do trabalho.

## O que foi feito

1. **Cerca de 60 requisições reais** contra o ambiente de produção do PNCP,
   partindo de três fontes primárias: o OpenAPI da API de Consulta, o Manual de
   Integração e o OpenAPI da API de Integração.
2. **Cadeia completa provada até o preço homologado**, sem token: varrer
   contratações → obter itens → obter resultado do item.
3. **Nota de pesquisa** em `docs/pesquisas/api-pncp-viabilidade-pesquisa-de-precos.md`,
   com cada afirmação marcada `[provado]` ou `[hipótese]`, diagrama da
   arquitetura que os achados impõem, tabela de riscos e uma seção do que **não**
   foi verificado.
4. **Coleção Postman** em `docs/pesquisas/postman/`, com asserções que verificam
   cada achado da nota. Funciona como guarda de frescor: asserção vermelha
   significa que a API mudou e a nota está errada.

## Descoberta que sustenta o recorte

**Nenhuma das interfaces do PNCP pesquisa pela descrição do item.** A busca do
portal casa o termo contra o *objeto da contratação*. A prova: uma contratação
municipal com 223 itens, cujo item 181 é um microscópio digital, não aparece na
busca por "microscópio digital" restrita ao Pará — os 38 resultados eram compras
cujo objeto mencionava equipamento hospitalar.

Consequência direta: pesquisar preço por item exige percorrer as contratações,
baixar os itens de cada uma e **construir índice próprio sobre as descrições**.
E essas descrições são texto livre de até 2048 caracteres, escrito por servidor
diferente em cada município, com os campos de catálogo vindo nulos.

O recorte de banco de dados não precisou ser justificado por conveniência de
orientação. Ele apareceu sozinho, na primeira tarde de teste.

## Armadilhas registradas

| Armadilha | Efeito |
|---|---|
| Paginação silenciosa | `/itens` devolve 10 de 223, com HTTP 200 e sem cabeçalho de total. 95,5% dos dados somem sem aviso |
| Filtro ignorado sem erro | `status=encerrada` não filtra nada; `status=encerradas` filtra. Sem mensagem, sem diferença aparente |
| Busca sem `User-Agent` | O servidor derruba a conexão, sem devolver código HTTP |

A primeira é a que corromperia uma cotação: valor estimado errado com aparência
de correto, e nenhum teste de "a requisição funcionou" pega.

## Verificação

```
API de Integração  → 15/15 com 200, média 217 ms, sem token
API de Consulta    → fora do ar às 09h52; degradou 500 → 504 → 502 → 503
                     até 11h20; voltou às 11h33 com 200 em 0,45 s
Varredura PA/mês   → 821 contratações, 17 páginas, 7,9 s
Coleção Postman    → todas as asserções passando na validação
```

## Decisão embutida nos achados

A dependência da API não documentada (`/api/search/`) foi classificada como
risco alto na primeira leitura e **rebaixada para baixa** depois que o serviço
de consulta voltou: o caminho crítico — varrer, baixar itens, indexar — é
percorrível inteiramente por interfaces documentadas. A busca por termo virou
conveniência, não alicerce.

## Próximo passo concreto

Confrontar o `valorUnitarioHomologado` com o texto da IN SEGES/ME nº 65/2021: a
Instrução admite preço praticado em contratação pública como parâmetro, em que
ordem de preferência e com quais ressalvas? É o que decide se o dado que a API
entrega serve como **fundamentação legal** do valor estimado, e não apenas como
número plausível.
